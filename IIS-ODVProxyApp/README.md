# ODV Proxy App (IIS)

Minimal IIS application that only reverse-proxies ODV log endpoints:

- `POST ./log` → System Log server (e.g., `http://localhost:3001/log`)
- `POST ./userlog/record` → User Log server (e.g., `http://localhost:3002/userlog/record`)

## Requirements

- IIS URL Rewrite module
- IIS Application Request Routing (ARR) with proxying enabled
- Windows PowerShell 5.1 (`powershell.exe`), run as administrator, for the setup script

The user-log server compares the browser's Origin/Referer host with the public host, and ARR replaces `Host` with the upstream address, so the user-log rule forwards the public host in `X-Forwarded-Host`. A rule may set a request header only when its server variable is in `allowedServerVariables`; the setup script takes care of that.

What the setup script changes:

- For the whole server, one thing: when a proxy rule is enabled it turns ARR proxying on (`system.webServer/proxy`, `enabled`). It unlocks no configuration section and does not change ARR's server-wide `preserveHostHeader`.
- For this application only: it allows exactly the server variables that the enabled rules set, as entries for the application's location in `applicationHost.config`. The application's own `web.config` never declares `allowedServerVariables`. A variable that the server or the site already allows is left alone, since a second entry for the same name is a configuration error.

Things to know:

- **Windows PowerShell only.** The script uses the `IIS:` drive of the WebAdministration module, which PowerShell 7 does not provide. It carries `#requires -PSEdition Desktop` and refuses to start in PowerShell 7, before it has changed anything.
- **It can be run again at any time.** The same switches give the same `web.config`, byte for byte, and the same allow list. Switching `-ForwardClientHeaders` on or off rewrites the rules to match.
- **`-WhatIf` changes nothing.** It shows what would be done; the final check is skipped then.
- **It ends with a check.** After the application is in place the script reads the allow list back and fails with an error if a server variable that a rule sets is not allowed, because IIS would then answer every proxied request with `500`.
- **Run the setup script again after an upgrade.** The user-log rule has to forward `X-Forwarded-Host`. With a `web.config` generated by an earlier version the user log server answers browser posts with `403`, unless ARR's `preserveHostHeader` is on. A rerun also repairs an installation where an earlier version of the script had written `web.config` without the variables its rules set.
- **The user-log upstream (`-UserLogUrl`) must be a loopback address** (`localhost`, `127.0.0.1` or `[::1]`). The user log server trusts `X-Forwarded-Host` from loopback only; the script warns about any other address.
- **The allow-list entries stay.** They are written for this application's location in `applicationHost.config`. The script has no uninstall, so they remain after the application is removed, and after `-ForwardClientHeaders` is switched off, until an administrator deletes them. An allowed variable that no rule sets has no effect.
- **What the script does not undo.** A server where an earlier version of this script was run with `-ForwardClientHeaders` has the configuration section `system.webServer/rewrite/allowedServerVariables` unlocked for the whole server, and it stays unlocked: the script no longer unlocks it and does not lock it again, since other applications may rely on it by now. The same goes for ARR's `preserveHostHeader` if an earlier version set it.
- **A later server-wide entry makes a duplicate.** If an administrator later allows one of the variables for the whole server or the site, the entry for this application's location becomes a second entry for the same name. IIS treats that as a configuration error and the proxy answers `500.19` until the entry for the application's location is removed.
- With `-ForwardClientHeaders` both rules also set `X-Forwarded-For` and `X-Forwarded-Proto`, and the system-log rule sets `X-Forwarded-Host`.

## Deploy

Use the repository-root script `scripts/Setup-IIS-ODVProxy.ps1` (run from the repository root, not from this folder) to:
- Create the IIS application (default path `/ODVProxy`)
- Generate `web.config` from `web.config.template`
- Toggle each proxy rule on/off
- Point rules to your target backend URLs

## Test

From the repository root, run `scripts/Test-ODV-IISProxy.ps1 -BaseUrl https://your-host/ODVProxy/`. It posts one
system-log and one user-log request and exits 0 when both return HTTP 2xx, otherwise 1.
