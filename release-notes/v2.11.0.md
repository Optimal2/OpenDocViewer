## Changes Since v2.10.0

PDF signatures become visible in the viewer, every displayed page can be fine-tuned in zoom, position, rotation and image, and two compared pages can be aligned in new overlay and curtain views that print as one composed page. The viewer shares the OMP light/dark choice with the other OMP apps on the same host and each installation can choose its default theme; the toolbar, manual dialog and printing get refinements and fixes, the bundled manuals are rewritten, the lockfile resolves the advisories published since v2.10.0, including the body-parser fix for CVE-2026-111181 in the optional log servers, and each release now carries a CycloneDX SBOM.

### PDF signatures

- **PDF signatures are read and shown.** Signed PDF files get a signature symbol next to the document label ("Doc n", shown when several documents are loaded) in the thumbnail strip, a discreet symbol on every page thumbnail of a signed file, and one signature overview button in the toolbar listing every signed document. The sticky document header at the top of the strip now has the same look and signature symbol as the inline one and appears only once the current document's own header has scrolled out of view (in v2.10.0 a plain label appeared as soon as the strip was scrolled). The dialog shows signer, signing time (local time), reason, integrity (intact, modified after signing, digest mismatch, invalid, format not supported, unreadable) and — when ODVGateway v0.1.44 with `signatures.enabled` answers — the server's trust verdict with a plain-language explanation for each of the gateway's reason codes; otherwise the trust line reads "Not checked" with an explanation of why (the document was not opened through ODVGateway, the gateway has signature validation switched off, or the gateway gave no usable answer). When several files of a document are signed, the dialog shows one tab per signed file. The browser-side parser (pdf-lib, pkijs, asn1js) verifies the signed digest and the signature over the ByteRange bytes in a worker; a signature that cannot be parsed is reported as unreadable, never as an error that breaks rendering. A PDF whose inspection cannot complete is never reported as unsigned: encrypted PDFs, PDFs larger than 64 MiB, PDF structures the parser cannot read, and inspections where the signature worker fails or exceeds its 30-second limit get the signature symbols and an overview entry with one "Signature unreadable" result, even when the file carries no signature.
- **Security of the signature path.** Signatures are discovered independently of PDF headers (prefixed files included), the integrity rules were hardened against bypasses found in review (bytes appended after a signature are reported as modified after signing unless a later signature that itself verifies covers them; whether a certification signature permits a later change is judged only by ODVGateway's trust verdict), the inspection queue is bounded, worker recovery is limited, gateway trust is restricted to the viewer's origin and gateway source-pack documents are validated.
- **The first page is never delayed.** Inspection starts only after the first page is shown, runs in a worker on bytes the viewer already holds, one PDF at a time; unsigned PDFs skip loading the certificate stack (pkijs, asn1js) but are still parsed for signature fields in the worker. Junk-prefix and comment-run probing are linear for every line-ending style, so large files stay fast. Two runtime-config keys keep it out of the way entirely: `pdfSignatures.enabled: false` turns inspection off (no worker bytes, no gateway request, no symbols) and `pdfSignatures.inspectAfter: 'allPages'` defers it until the whole loading run is ready (it also starts after an aborted loading run). `pdfSignatures.thumbnailPageBadge: false` hides only the per-page symbol.
- **Accessible overview.** The signature overview has no interactive controls nested in list options; while the details dialog is open on top, the overview is inert and hidden from assistive technology, so only one dialog is announced.

### Page fine tuning and comparison

- **Fine tuning for the displayed page.** A **Fine tuning** toolbar button shows an adjustment panel above the displayed page, or above both pages in compare mode. The panels start hidden; the choice lasts for the session, survives entering and leaving compare mode and the overlay and curtain views, and hiding the panels keeps every adjustment. Each panel holds zoom in 0.1 % steps, position (drag the page, type X and Y, or use the arrow keys on the focused move button, Shift for 10 px), rotation in 0.1° steps with 90° buttons that keep the fine rotation (4.6° → 94.6°), brightness, contrast, grayscale and invert, and three resets: all, layout (zoom, position, rotation) and image (brightness, contrast, colour). While a panel is open, Ctrl+wheel zooms only that page.
- **Adjustments are remembered per page for the session.** Zoom, position, rotation and image adjustments are kept per original page number in each pane: returning to a page restores them, an unvisited page starts neutral, and opening a new set of documents clears them. They are held in memory only and never saved. In v2.10.0, brightness, contrast and rotation reset whenever the page changed. Compare mode's per-pane zoom, which in v2.10.0 stayed the same while paging and reset when compare mode was entered or left, now also follows the page and is kept across compare mode changes.
- **Overlay view.** In compare mode with two pages shown, a toolbar button opens an overlay view that stacks page B (right) on top of page A (left) with the same image adjustments as side by side. An opacity slider (0–100 %, default 50 %) sets the opacity of the top page, Swap changes which page is on top, and the pages are calibrated with both fine-tuning panels, by dragging or Ctrl+wheel on the top page, or in a nudge mode where the arrow keys move only the top page. The reset button ("Reset to the alignment from the compare view") restores the alignment and image settings the view opened with, and the copy button ("Copy the calibration as JSON (for support)") copies both pages' settings as JSON for support cases. Close or Escape returns to the compare view and keeps the calibration.
- **Curtain view.** Shows the two calibrated pages divided by a draggable border, page A on one side and page B on the other, horizontally or vertically; the border moves by mouse, touch or arrow keys (1 %, Shift 10 %), and corner labels name the page on each side. It opens from the overlay view, or from the compare toolbar once the overlay view has been opened in the current compare session (immediately when the overlay view is switched off). Both views open with the two pages' fine-tuning panels expanded. Close or Escape returns to where the curtain was opened.
- **Printing the new views and fine-tuned pages.** The overlay and curtain views each have a Print button that prints one composed page of the visible area (current opacity or border, both pages' zoom, position, rotation and image) through the same print dialog and its usual outputs (direct print, Print via PDF, and Save PDF where `print.pdf.allowDownload` is on); the print log records one page. Printing the active page or both compare pages now prints each page as fine-tuned, inside its original page frame; printing a page range or all pages still prints the unedited source pages.
- **Compare mode refinements.** Per-pane zoom now reaches 10–800 % (was at most 400 %), and its 10 % step buttons keep a fine-tuned fraction. The zoom controls sit in a hover-expanding zone behind the pane's selection ring instead of overlapping the page. In compare mode the toolbar's reset button resets everything the page's panel can reset, and the toolbar's 90°, brightness and contrast controls act on the target page, with brightness and contrast showing its current values. Side-by-side panes with an image adjustment no longer redraw their canvas on every viewer update.
- **Per-site switches.** `fineTune.enabled` (default `true`) is the master switch: `false` removes the Fine tuning button and panels, the per-pane zoom buttons in compare mode, and the overlay and curtain views including their printing, while ordinary viewing, side-by-side comparison and normal printing remain; per-page session memory of the toolbar's rotation, brightness and contrast applies in both cases. With fine tuning on, `compare.overlay.enabled`, `compare.curtain.enabled` and their `print.enabled` children (all default `true`) remove each view or only its Print button; with the overlay off, the curtain uses the compare view's own alignment. `compare.adjust.toolbarMode: 'hide'` hides the toolbar's 90°, brightness, contrast and reset controls in compare mode while a page's panel is expanded (default `'mirror'` keeps them). For the boolean switches only a literal `false` turns a feature off; missing or malformed values use the default.

### Viewer

- **Default theme per installation.** `theme.defaultMode` (`"system"` default, `"light"`, `"dark"` or `"normal"`) in the site configuration decides the theme while the browser has no stored choice; a System choice saved by v2.10.0 is not carried over and counts as none. Any other stored choice, including an explicit System in the shared OMP preference, still wins, so the setting only sets the first impression.
- **Theme.** The viewer shares the OMP light/dark choice with the other OMP apps on the same host through the shared `OMP_THEME_PREFERENCE` preference (a host-wide cookie kept for one year plus a localStorage mirror, with validated revisions); an opt-in cross-origin bridge for framed use is limited to the exact origins in `theme.bridge.allowedOrigins` (empty and off by default). The viewer keeps the Normal palette and preserves focus visibility, print surfaces and selection contrast across themes.
- **Toolbar.** A "Larger toolbar buttons" checkbox in the theme menu (default on, stored like the other preferences; `toolbar.largeButtons: false` makes compact the site default), 2 px air between group frames and their buttons without changing the toolbar height, and equal-width 1:1 / 1:X zoom buttons.
- **Visual fixes.** Disabled buttons in the print-selection view are no longer faded out: they keep readable text (at least 4.5:1 contrast in every theme) with a light solid border in the theme's border colour; the manual overlay is readable in the dark theme (its text colours follow the viewer theme, tips and warnings are tinted instead of fixed light boxes); the manual search field shows one clear button instead of two.

### Printing

- **Print jobs keep their page images.** Page images handed to a print or PDF job stay valid until the job has finished, even when a resolution boost replaces a page image meanwhile, and are released when printing completes or is cancelled and when a PDF prebuild, a benchmark or the viewer session ends. A resolution boost also no longer revokes a page image that is still displayed, and the worker's fallback path no longer caps an explicit boost scale at the default ceiling (the pixel and render-surface caps still apply).
- **Custom page ranges.** An entry with more than two endpoints, such as `1-2-3`, is rejected as an invalid range instead of being silently shortened to `1-2`.
- **Recipient label.** When `userLog.ui.fields.forWhom.required` is `true`, the print dialog labels the field "Recipient *" instead of "Recipient (optional) *"; an optional recipient still reads "Recipient (optional)".

### Manual and localization

- **Manual dialog.** The help dialog uses near full width with a sticky contents tree on the left built from the manual's headings; in-text links, including the bundled manuals' image lightbox, work inside the dialog, and closing it returns focus to the help button. The search highlights the right text also where a character's lower-case form is longer (for example İ), counts only the hits it highlights, finds text inside highlights the manual itself contains, and Escape clears the search from anywhere in the search row before a second Escape closes the dialog; in forced-colors mode the focused field gets a visible outline. The manual HTML is sanitized as before.
- **Rewritten bundled manuals.** The default manual in `help/default/` is rewritten as a start guide plus three topic guides in Swedish and English, each also as a PDF: the start guide and the selection and advanced-features guides are revised, and the comparison guide is new. Every screenshot is taken from the current viewer with one neutral example document set. A site manual in `help/site/` still takes precedence.
- **Localization files are never served stale.** The locale file URLs carry a hash of the locale files' content, and the bundled IIS `web.config` serves `locales/` with `no-cache, must-revalidate`, so a new release never shows old strings unless the site configuration pins `i18n.version` (the default `auto` uses the hash).

### Dependencies, security and packaging

- **body-parser 2.4.0 for the optional log servers.** The npm override for body-parser moves to `^2.4.0`, fixing CVE-2026-111181 (GHSA-27r3-jxmh-p828, high: denial of service through trailing bytes after a compressed request body) in the Express stack of the optional system-log and user-log servers; v2.10.0 resolved body-parser 2.3.0. The viewer bundle itself does not contain body-parser.
- **Further advisories resolved through the lockfile.** Six more advisories published after v2.10.0 affect three non-development packages in its lockfile. v2.11.0 resolves all of them, and none is reachable with the viewer's own use. DOMPurify 3.4.17, bundled in the viewer, fixes GHSA-cg2g-xh64-v4q7 (critical), GHSA-mrv2-3pqr-j5jr (high) and GHSA-c6gr-qvv4-5v3f (low); they require the `SAFE_FOR_TEMPLATES` option with DOM output, `IN_PLACE` with hooks, or the XHTML parser, none of which the viewer's sanitizer calls use. follow-redirects 1.16.1 fixes CVE-2026-111755 and CVE-2026-111756 (high) in axios's Node.js adapter, which neither the viewer bundle nor the log servers use. ip-address 10.7.4 fixes CVE-2026-111997 (moderate) behind the log servers' IPv6 rate-limit keys, which only receive addresses that Node.js has already validated.
- **Software bill of materials.** Starting with this release, each GitHub release carries `OpenDocViewer-sbom-vX.Y.Z.cdx.json`, a CycloneDX SBOM of the runtime dependencies generated from the release's own lockfile, next to the dist archive. `SECURITY.md` has a new EU Cyber Resilience Act section covering the maintainer, private vulnerability reporting, the SBOM and the reporting obligations.
- **PDF.js 6.4.299, pinned exactly.** The page renderer moves from `pdfjs-dist` 6.3.289 to 6.4.299 and is pinned exactly in the npm manifest and lockfile, so fresh installs stay on the version covered by the rendering regression fixtures. Annotation and signature rendering (visible and invisible signature appearances, widget annotations) is locked by Vitest and Playwright fixtures so the next renderer bump cannot move it silently.
- **Dependency baseline.** pkijs and asn1js 4.0.0 (new in this release; asn1js is a peer dependency of pkijs, so the bundle carries one asn1js copy), React 19.3.1, i18next 26.5.10, react-i18next 17.1.8, DOMPurify 3.4.17, file-type 22.2.0, Express 5.3.0, express-rate-limit 8.7.1 and dotenv 18.0.8; build and test tooling on Vite 8.3.5, Vitest 5.0.5, jsdom 30.1.3 and Playwright 1.64.1. `npm audit` reports no advisories.
- **OMP packaging (internal).** The OMP component `opendocviewer-web` is versioned in `omp-components.json` alongside the release and was bumped for OpenModulePlatform's deterministic artifact packer (byte-stable artifact packages); CI now fails every push and pull request whose component versions are out of lockstep, and the validator helpers and `bump-version.ps1` were synced from OpenModulePlatform. Agent documentation regenerated.

## Upgrade Guidance

Upgrade v2.10.0 deployments to v2.11.0. No site-configuration change is required. Signature inspection is on and never delays the first page. Only ODVGateway v0.1.44 with `signatures.enabled: true` returns a trust verdict; otherwise the trust line reads "Not checked", and its explanation says whether the document was not opened through ODVGateway or the gateway has signature validation switched off. Behind an ODVGateway older than v0.1.44, which has no signature endpoint, every signed PDF sends one request that the gateway answers with 404, and the explanation says that the server could not check the signature; upgrade ODVGateway to v0.1.44 together with the viewer (it can keep `signatures.enabled: false`; follow its upgrade guidance, because a gateway whose `maxSourcePackFrameBytes` was raised above about 170 MiB needs a matching signature setting to start). Encrypted PDFs, PDFs over 64 MiB, PDFs the parser cannot read and PDFs on which the signature worker fails or exceeds its 30-second limit show an "unreadable" signature symbol even when they are unsigned, and behind ODVGateway they also send the trust request; after four worker failures, every further PDF in the viewer session does so too. Sites that want no signature reading, or where such files are common, set `pdfSignatures.enabled: false`. Page fine tuning and the overlay and curtain views, including their printing, are available by default. Sites that want to hide the new controls set `fineTune.enabled: false`; this also removes the per-pane zoom buttons that compare mode had in v2.10.0, and rotation, brightness and contrast set from the toolbar are still kept per page for the session instead of resetting when the page changes. Sites that only want to drop one view or its Print button set the matching `compare.overlay.*` or `compare.curtain.*` key to `false`. The `compare` block in the new `odv.site.config.sample.js` switches both views off; leave it out when copying the sample unless that is intended. Printing the active page or both compare pages now prints fine-tuned pages as adjusted; range and all-pages printing are unchanged. Sites that run the optional system-log or user-log server update its dependencies from this release's lockfile to get body-parser 2.4.0 and ip-address 10.7.4. If the IIS site uses its own `web.config`, add the `locales/` cache rule from the bundled one; a reverse proxy, CDN or portal in front of the viewer needs the same rule (`no-cache, must-revalidate` for `locales/*/*.json`, never `immutable`). Sites that pin `i18n.version` change it or set it to `auto`. The theme is now kept in the shared `OMP_THEME_PREFERENCE` cookie and localStorage entry: a user's existing Light, Dark or Normal viewer theme is carried over when the host has no shared choice yet; otherwise the host's shared choice applies. Sites that want a fixed first theme set `theme.defaultMode`; it also applies to browsers whose v2.10.0 choice was System, because that choice is not carried over. Build and Node.js requirements are unchanged from v2.9.0.
