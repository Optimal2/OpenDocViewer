# AI Agent Documentation

OpenDocViewer keeps a generated agent documentation packet under
`docs-agent/`. It is generated by AgentDocMap from the existing JSDoc comments
and source structure. The generator must not require AgentDocMap-specific
comments in OpenDocViewer source files.

## Agent Read Order

When an AI agent starts work in this repository, use this order:

1. `docs-agent/AGENT_CONTEXT.md`
2. `docs-agent/MODULES.md`
3. `docs-agent/ENTRYPOINTS.md`
4. `docs-agent/DEPENDENCIES.md`
5. `docs-agent/FILE_MAP.md` for the area being changed
6. `docs-agent/SYMBOL_INDEX.md` for JSDoc-backed symbols
7. `docs-src/CODEX_DEVELOPMENT.md` for repository workflow rules

The generated packet is an orientation layer, not a replacement for reading the
source before editing.

## Regenerating

AgentDocMap is expected to be cloned next to OpenDocViewer in local development:

```text
<workspace>/AgentDocMap
<workspace>/OpenDocViewer
```

Regenerate the committed packet with:

```bash
npm run doc:agent
```

The command writes `docs-agent/` with stable metadata so the files can be
committed without changing on every run.

If AgentDocMap is elsewhere:

```bash
npm run doc:agent -- --agentdocmap-root <path-to-AgentDocMap>
```

## Pinned Environment

The same input must give the same bytes in CI and locally, so
`scripts/agent-docs-environment.json` pins the three things that otherwise
change the output. The Agent Documentation and Release workflows read it, and
`scripts/generate-agent-docs.mjs` (also used by `scripts/local-ci.ps1` step 4)
enforces it before AgentDocMap runs:

- `node`: the exact Node version. CI must run it. Locally a different ambient
  Node is allowed: the generator prints a `NOTE` and runs AgentDocMap with the
  pinned binary from `ODV_AGENT_DOCS_NODE`, fnm, or nvm, and fails with an
  install hint (`fnm install <version>`) when none is found.
- `agentDocMap.revision`: the AgentDocMap commit. The checkout must be at this
  commit without tracked modifications, and `node_modules/.package-lock.json`
  metadata must match its `package-lock.json`. This does not hash installed
  package files: local patches, missing files or linked dependencies can pass
  this check. Use a clean `npm ci` installation to reproduce CI's dependency
  tree; freshness validates generated output, not installed-file integrity.
- `collation`: AgentDocMap sorts paths and names with `localeCompare()` and no
  locale, which follows the OS (sv-SE on a Swedish Windows desktop, en-US on a
  `C.UTF-8` Linux runner). On Windows the OS locale cannot be overridden by
  environment variables, so `scripts/agent-docs-collation-shim.mjs` is preloaded
  into AgentDocMap and its JSDoc child and makes locale-less `localeCompare()`
  use the pinned locale. It then sorts `probe` and fails unless the result
  equals `expectedOrder`.

To upgrade AgentDocMap or Node, change the pin, run `npm run doc:agent`, and
commit the pin together with the regenerated `docs-agent/`.

## Release And CI Expectations

- Update `docs-agent/` when source structure, public JSDoc, package
  dependencies, startup flow, or major module responsibilities change.
- Run `npm run doc:agent` during release preparation.
- The release helper includes `npm run doc:agent` in pre-release validation.
- The GitHub "Agent Documentation" workflow regenerates `docs-agent/` and fails
  if the committed packet is stale. `scripts/local-ci.ps1` step 4 (the pre-push
  gate) does the same with the same comparison script.

## Freshness Comparison

Both gates run `npm run doc:agent` and then
`node scripts/verify-agent-docs-fresh.mjs`. AgentDocMap deletes and rewrites
`docs-agent/` on every run, so after regeneration the directory holds exactly
what the pinned generator emits. The script then requires that `docs-agent/`
is identical in the working tree, the index and `HEAD`, and rejects:

| State under `docs-agent/` after regeneration | Query | Rejected because |
| --- | --- | --- |
| Tracked file with different content (`M`) | `git diff HEAD` | `HEAD` is stale. |
| Different raw bytes, including CRLF instead of LF | Raw Git blob hash against `git ls-tree HEAD` | Clean filters and Git's stat cache must not hide a byte difference. |
| File in `HEAD` that the generator no longer writes (`D`) | `git diff HEAD` | `HEAD` keeps an obsolete file. |
| Any staged change, including fresh output staged on a stale `HEAD` | `git diff --cached HEAD` | The gate checks `HEAD`, which is what gets pushed; staged content is not. |
| Untracked file, for example new generator output never added | `git ls-files --others` | `HEAD` lacks a file the generator writes. |
| Gitignored file | `git ls-files --others` (no exclude rules) | Generator output that git ignores could never be committed; since the directory is regenerated from scratch, an ignored file there is generator output. |
| `assume-unchanged` or `skip-worktree` index flags, even without a disk edit | `git ls-files -v` | Masking flags make ordinary Git queries incomplete. Clear them before checking freshness. |

The working-tree comparison hashes raw bytes with Git's blob header and the
repository's object hash algorithm, independently of clean filters, attributes,
`core.autocrlf` and cached file stats. CRLF output is rejected when HEAD holds LF,
even if a preceding filtered `git diff` cached it as clean. Merely setting
`core.autocrlf=false` would not bypass that cache or explicit text attributes.
The committed packet already uses LF; no blob renormalization is needed.
After generation, LF output is accepted even in a CRLF-configured checkout.
Files outside `docs-agent/`, staged or not, are never considered. Clear masking
flags with `git update-index --no-assume-unchanged -- <file>` and
`git update-index --no-skip-worktree -- <file>`; the gate never changes the index.
The CLI realpaths both its entry argument and module filename so invocation
through a directory junction, symlink or drive alias still runs the comparison.
Imports remain quiet for helper consumers; CLI failures print a diagnostic.

Why the two sides are equivalent: a fresh CI checkout has index = `HEAD` and no
untracked files before generation. There the staged query is always empty and
the other two reduce to "generator output = `HEAD`". Locally, comparing every
query against `HEAD` (instead of the index, as the earlier
`git diff --exit-code -- docs-agent` did) prevents staging from moving the
comparison base. Equivalence requires the same HEAD and regenerated bytes;
it does not promise identical local/CI environments or dependency contents.
Local staged `docs-agent/` changes on a fresh HEAD and masking index flags are
additional rejections that a clean CI checkout does not encounter. Commit or
unstage the former and clear the latter. Raw-byte comparison covers line endings
regardless of local Git configuration. Deleting a tracked file by hand is not a
rejectable state on its own: the generator writes it back before the
comparison runs. `scripts/verify-agent-docs-fresh.test.mjs` pins these rules.

Right after regeneration, `git status --short -- docs-agent` can still list
roughly 30 modified files while the gate correctly reports "is fresh". Git's
stat/index view can retain checkout-conversion metadata even though generated
content equals HEAD. For example, `git status --porcelain=v2` can show
`1 .M N... 100644 100644 100644 <oid> <oid> docs-agent/REPORT.md`: the identical
OIDs describe HEAD and index, not the working-tree bytes. Check
`git hash-object --path docs-agent/REPORT.md docs-agent/REPORT.md` against
`git rev-parse HEAD:docs-agent/REPORT.md` for normalized content, and
`git hash-object --no-filters docs-agent/REPORT.md` for actual bytes. Only the
last comparison proves byte equality; the gate now performs that raw comparison
for every committed file. A status marker alone does not invalidate a fresh run.

The Linux Agent Documentation workflow proves that a clean checkout, pinned
Node/AgentDocMap, and `npm ci` regenerate the committed packet on that runner.
It does not verify local dependency file contents, Windows path aliases, or
every possible OS/filesystem; local regression tests cover those named cases.

Do not put private deployment values, customer-specific notes, credentials, or
protected payload examples in generated public agent documentation.
